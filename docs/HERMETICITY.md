# Hermeticity

This file lists each input of the Node build and where it comes from.
The build is not fully hermetic. The gaps are named here.

## Rungs

Each input has a rung. A lower rung is stronger.

| Rung | Meaning |
|---|---|
| 0 | Pinned address and pinned checksum |
| 1 | Pinned checksum, with the checksum computed here from a download |
| 2 | Generated by a named tool |
| 6 | Stays on the host |

## Host inputs

### macOS SDK

The Apple SDK license does not allow a pinned copy in a public repository.
`toolchain/sdk.bzl` selects an SDK from the host.
It writes the path, the version, and a digest of `SDKSettings.json` to `info.json`.
The repository also links the SDK files as `sdk/`, and `//toolchain:sysroot_files` declares them as inputs of the build action.
A change to any SDK file makes a new cache key.
The tarball records the same values in `BUILDINFO.json`.

Two paths are not linked, because Bazel cannot declare them: `Ruby.framework` (a symlink loop) and `usr/share/man` (file names with `:`).
The build does not read them.

The action still reads the SDK at its host path, from `info.json`. The declared files make the cache key correct.
They do not make the action read the declared copy. A change to use `sdk/` in the action is a later step.
`tests/sdk_inputs_test.py` checks the declared files.

Set `ROOTBEER_MACOS_SDK` to select a different SDK.

`ld64.lld` 19 cannot read a `.tbd` file that lists `arm64e.x1`.
`toolchain/sdk.bzl` skips an SDK with this architecture.
A host that has only such an SDK fails with a clear message.

### Optional pinned macOS SDK

`--config=pinned-sdk` selects an SDK from a private tarball. The default stays the host SDK.
No build needs this config. The Mac and the macOS CI runner do not use it.

The Apple license does not allow a public copy of the SDK. Follow these rules:

- Never commit the tarball.
- Never upload the tarball.
- Never add the tarball to an artifact, a shared cache, or a public URL.
- Do not use this config with a remote service. The SDK files are action inputs, so a remote executor receives them.

The config turns off the remote executor, the remote cache, the event service, and the remote downloader.
Put `--config=pinned-sdk` last on the command line, because a later flag can turn a service on again.
Bazel keeps a copy of the tarball in the local repository cache, and the extracted files in the output base.
Do not share these directories, and do not share a `--disk_cache` directory that this config used.

To make and use a tarball:

1. Run `python3 tools/pack_macos_sdk.py --out ~/private/MacOSX.sdk.tar.gz`. Use `--sdk PATH` to select an SDK from Xcode or Command Line Tools.
2. Add the two printed `common:pinned-sdk` lines to `~/.bazelrc`.
3. Run `bazel build --config=pinned-sdk //runtimes/node:node_22`.

The helper refuses an output path in a git work tree, and it writes the file with mode 0600.
The tarball must hold exactly one `*.sdk` directory. The repository rule refuses a wrong checksum, a missing tarball, and an SDK that `ld64.lld` cannot read.
With the config off, the rule ignores the address and the checksum.

With the config on, the SDK is rung 1, and `info.json` records `"source": "pinned"` and the tarball checksum.
The action reads the declared `sdk/` files, not a host path.
`info.json` goes into the published `BUILDINFO.json`, so it never records the address.
The POSIX tools below still come from the host, so this config does not make the macOS build fully hermetic.
The compiler is the pinned LLVM in both modes.

CI may use this config only if the private tarball is available to a private runner.
The repository has no such secret, and CI leaves the config off.
A job that turns it on must not save a Bazel cache to the Actions cache, and it must not upload the tarball as an artifact.

### POSIX tools

The action `PATH` holds the tool wrappers, then `/usr/bin`, then `/bin`.
Node's configure and build steps call `sh`, `sed`, `cp`, `mkdir`, and similar tools.

- **Linux:** The build image supplies these tools. They are BusyBox, pinned by checksum (rung 0).
- **macOS:** These tools come from the host. The result does not record their versions (rung 6).

### Sandbox limits

The Bazel sandboxes on macOS and Linux do not hide host read paths.
A step can still read `/usr/include` or `/usr/lib` if a flag points there.
The Bazel sandbox removes the environment and limits write paths.
It does not prove that the build reads only declared inputs.

The evidence for this claim is narrower:

- `LinkCheck.test_only_system_libraries` reads the needed libraries of the binary.
- The compiler gets `-isysroot` or `--sysroot`, and `-nostdinc++`.
- The Linux build runs in a container with no host compiler.

## Linked libraries

The macOS binary links these libraries only. Some lines link fewer.
For example, the Node 18 binary links only `libSystem.B.dylib` and CoreFoundation.

- `libSystem.B.dylib`
- `libobjc.A.dylib`, when a framework needs it
- CoreFoundation and Security frameworks

libc++ and libc++abi link statically.

The Linux binary links glibc libraries and `libgcc_s` only.
These libraries come from the host at run time.
Node passes `-latomic` to the linker on Linux with Clang.
`MODULE.bazel` removes `libatomic.so` from the sysroot, so the linker selects `libatomic.a`.
The sysroot ships glibc 2.31, so the binary cannot import a newer symbol.
`GlibcFloor` in `runtimes/node/tests/hermetic_test.py` fails when any imported symbol needs glibc newer than 2.31.
The measured floor of the current builds is glibc 2.25.

## Known limits

- `-Wl,-no_fixup_chains` is required on macOS.
  A binary with static libc++ and chained fixups crashes at startup with exit code 139 on Darwin 27.
  This program is enough to show it, with no Node code:
  `#include <iostream>` and `int main() { std::cout << 1; }`,
  compiled with the pinned clang and `-nostdlib++`, and linked with the pinned `libc++.a` and `libc++abi.a`.
  - The crash is a call through a null pointer in `std::__1::__stdinbuf<char>::imbue`, from `DoIOSInit`.
  - `dyld_info -fixups` shows the vtable slots of the libc++ weak definitions as chained binds to
    `<weak-def-coalesce>/<symbol>`. The symbols are in the export trie of the executable, flagged weak.
    The binary has 687 such binds, and dyld 27 leaves these slots null.
  - Apple's `ld` makes the same crashing binary, so the pinned lld is not the cause.
  - `-Wl,-no_exported_symbols` removes the binds and the crash with chained fixups on, with `ld` and with lld.
    It is not usable, because native add-ons resolve the Node and V8 symbols from the executable.
  - `-Wl,-no_fixup_chains` keeps the classic weak-binding opcodes, and it works.
  - Stock Node does not meet this, because it uses the libc++ of the system.
  - I did not test other macOS versions. The flag is correct on all of them, and the cost is a larger relocation table.
- The LLVM libc++.a objects target macOS 14.0, and the linker warns about this.
  The practical minimum for the macOS artifacts is macOS 14.
- Byte-for-byte reproducibility is checked by a tool, not by a test. See [Reproducibility](#reproducibility).
- Node's `OPENSSLDIR` value comes from Node's own OpenSSL configuration.
  It is `/etc/ssl` on macOS and on Linux. This is a host path by design.

## Bazel settings

`.bazelrc` sets these. `tests/bazel_config_test.py` and `tests/repo_rules_test.py` check them.

| Setting | Effect |
|---|---|
| `common --lockfile_mode=error` | `MODULE.bazel.lock` is committed. A stale lock fails the build. It pins every registry file by hash. |
| `build --incompatible_strict_action_env` | An action sees a fixed `PATH`, not the `PATH` of the user. `node_build` also sets `use_default_shell_env = False`. |
| `build --sandbox_default_allow_network=false` | An action cannot use the network. The default sandbox allows it. A probe action reaches a host without the flag and fails with it. The network tests carry `requires-network`, so they keep their access. |
| `common --repo_env=BAZEL_DO_NOT_DETECT_CPP_TOOLCHAIN=1` | The build does not look for a host C++ compiler. |
| `common --repo_env=BAZEL_NO_APPLE_CPP_TOOLCHAIN=1` | `apple_support` does not look for Xcode. It ignores the setting above. |
| `register_toolchains("//toolchain/cc:all")` in `MODULE.bazel` | Each C++ action uses the pinned LLVM. `//tests:cc_toolchain_test` fails if a host compiler returns. On macOS the SDK stays a host input (rung 6). |

Every `http_archive` has a `sha256`. No repository rule downloads without a checksum, and no source comes from a Git ref.

## Reproducibility

The binary must not hold a path of the build machine. `BuildPaths` in `runtimes/node/tests/hermetic_test.py` fails when it holds
`/execroot/`, `bazel-out/`, or a sandbox path. It found three leaks:

- OpenSSL 3 `MODULESDIR` (Node 18 and newer). `0002-force-local-store.patch` sets it to `/nonexistent/ossl-modules`.
- The sysroot path in compiler output. The wrapper adds `-ffile-prefix-map={sysroot}=/sysroot`.
- The object paths that lld writes in the Mach-O symbol table (N_OSO). The link adds `-Wl,-S`.

`bazel run //tools:repro_check -- 22` builds one line twice, with no cache. The two workspaces have different paths
and path lengths, and different output bases. It compares the archives, and for a difference it lists the strings that
only one binary holds. `--compare A B` compares two existing archives, for example one from CI and one from a laptop.

Results, macOS arm64, no cache, two different paths:

| Line | Result |
|---|---|
| 26, 24 | Not run. |
| 16 | Not reproducible. 220,725 of 70,772,032 bytes differ, all in the startup snapshot (`node::blob_data`). |
| 18 | Not run. It has the same V8 snapshot patch as 16. |
| 20 | Not run. |
| 22 | Reproducible. Both archives have the same sha256 (`d9165531…bd33c`) when built at different workspace paths and output bases. |
| Linux, all lines | Not run. |

The startup snapshot is the cause for Node 16. Node 16 and 18 fix the V8 random seed but do not pass `--predictable`.
Before `0005-predictable-snapshot.patch`, the snapshot changed its length between builds, and the ICU data
after it moved: 19.7 MB differed. The patch fixes the length. The content is still not deterministic in the old V8.
I found no flag for that. Upstream needed V8 changes (Node 20 and later).

## Remote execution

`//toolchain/platforms:linux_x64_rbe` is a Linux x86_64 platform with `OSFamily=linux` and a pinned `container-image`.
`--config=remote-exec` makes it the target, host, and execution platform, and uses no local fallback.
The endpoint and the keys belong in `~/.bazelrc`.

- The Node build is one action. It runs 6 compile jobs with `--config=remote-exec` and 5 in Docker.
- `resource_set` (10 CPUs, 16 GB) applies only to local execution. The scheduler does not read it.
- The properties of the platform must match the properties of the worker exactly. The scheduler does not guess.
- The macOS build cannot run remotely, because the SDK comes from the host (rung 6).

What a real run shows, on a Buildbarn runner with a cap of 6 CPUs and 8 GiB:

| Item | Result |
|---|---|
| `bazel build --config=remote-exec //runtimes/node:node_16` | Pass. 758.8 s. Peak memory 3.0 GiB. |
| The same action, new output base, remote cache hit | 18.0 s. |
| `bazel build --config=remote-exec //runtimes/node:node_26`, 6 jobs | Pass. 1620 s. 180 s under the limit. Peak memory 6.31 GiB. One run. |
| The 6-job build again, from the merged tree | Remote cache hit, 33 s. Same sha256. |
| The same build, 5 jobs | Fail. The scheduler stopped the action after 1810 s. Peak memory 5.7 GiB. |
| `bazel build --config=remote-exec //runtimes/node:node_22` | Pass. 1378 s. |
| `bazel build --config=remote-exec //runtimes/node:node_24` | Pass. 1648 s. 152 s under the limit. |
| `bazel test --config=remote-exec //tests:cc_toolchain_test` | Pass. |
| `bazel test --config=remote-exec //runtimes/node/tests:hermetic_16_test`, 6 jobs | Pass. New build, 629 s. |
| `bazel test --config=remote-exec //runtimes/node/tests:hermetic_18_test`, 6 jobs | Pass. New build, 711 s. |
| `bazel test --config=remote-exec //runtimes/node/tests:hermetic_26_test`, 6 jobs | Pass. Remote cache hit for the build, 13 s. |
| Hermetic tests for Node 20, 22, and 24 | Not run. |
| Node 20 build | Not run. |

The `//runtimes/node:node_16`, 22, and 24 rows used 5 jobs. The job count is in the action key, so Node 22 and 24 now need a new build. Their times with 6 jobs are not measured.

Limits:

- `toolchain/cc/` registers the pinned LLVM and the Linux sysroot as the C++ toolchain, so `bazel test --config=remote-exec` passes analysis.
- The macOS SDK stays a host input through `toolchain/sdk.bzl` (rung 6). The macOS toolchain has this one host input.
- apple_support detects Xcode and ignores `BAZEL_DO_NOT_DETECT_CPP_TOOLCHAIN`. `.bazelrc` also sets `BAZEL_NO_APPLE_CPP_TOOLCHAIN=1`.
- The scheduler limit is the real limit, not memory. The SER9 scheduler stops an action at 1800 s by default.
  - The Bazel flag `--remote_timeout` does not change this limit.
  - A rule cannot change it. Bazel 9.1.1 removes the `timeout` key from `execution_requirements` (`TargetUtils.legalExecInfoKeys`).
  - A build that needs more than 1800 s needs a higher `defaultExecutionTimeout` in the scheduler configuration.
  - Node 26 has a small margin. A busy host or a larger release can pass the limit.

## Linux container

`runtimes/node/image/Dockerfile` makes a small image that holds only pinned files.
It has no package manager, no shell other than BusyBox, and no compiler.

| Input | How it is pinned |
|---|---|
| Unpack stage | `FROM` image with a `@sha256:` digest. It runs `dpkg-deb -x` and `ln` only. |
| Final stage | `FROM scratch`. Only `COPY` adds files. |
| Bazel | `ADD --checksum=sha256:`. This binary has its own JDK. |
| BusyBox and libraries | One `ADD --checksum=sha256:` for each `.deb`. |
| `.deb` address | `snapshot.debian.org/archive/debian/<timestamp>/`. The address cannot change. |
| CA bundle | `COPY trust/mozilla-no-emsign.pem`. It is the pinned test bundle of this repository. |
| `passwd`, `group`, `nsswitch.conf` | `runtimes/node/image/etc/` in this repository. |

The packages are `libc6`, `libgcc-s1`, `libstdc++6`, `zlib1g`, `libzstd1`, `liblzma5`,
`libxml2`, `libicu72`, `libtinfo6`, `bash`, `dash`, and `busybox-static`. The pinned LLVM Linux tools load these libraries.
`ld.lld` needs `libxml2`, `libicu72`, and `liblzma5`. The other tools need `libstdc++`, `libz`, and `libzstd`.

`runtimes/node/tools/pin_debs.py` prints the `ADD` lines for a snapshot timestamp.
A reviewer can run it again and compare the checksums.
This tool is the only step that reads an index that is not pinned. The build never runs it.

`tests/docker_test.py` fails the build when a `FROM` has no digest,
an `ADD` has no checksum, a `.deb` does not come from the snapshot archive,
or a `RUN` calls `apt`, `curl`, or another tool that fetches inputs.

BusyBox has no `find -delete` and no `bash`.
`MODULE.bazel` uses `find -exec rm -f {} +`.
The image has GNU `bash` from a pinned `.deb`, because Bazel runs `patch_cmds` and its test scripts with `bash`.
A BusyBox `sh` runs its own applets before it looks at `PATH`.
That hides a wrapper with the same name, for example `ar`.
For this reason `/bin/sh` is `dash`, and the image has no `ar` link.

### Remaining Linux gaps

- Docker, the kernel, and the CPU come from the host.
- The Bazel sandbox inside Docker is `processwrapper-sandbox`. It does not hide host read paths.
- BusyBox applets have different options than GNU tools. A new build step can need a GNU option.
- `snapshot.debian.org` is a single host. The checksums stop a changed file but cannot stop an outage.
- `tools/repro_check.py` compares two builds, but it has not run on Linux. The image content is not proven reproducible byte for byte.
